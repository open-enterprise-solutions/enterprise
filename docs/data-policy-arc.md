# Data Policy — Architecture Arc (design)

> **Status:** DESIGN — captured from the 2026-06-11 design session, no code yet.
> Builds on the landed L1–L4 query stack (`query-language-arc.md`) and precedes /
> accompanies the totals-table arc (`temp-db.md` §9 neighbourhood, accounting roadmap).
>
> **One sentence:** access rules, period close, and read-only enforcement become
> **declarative platform-level policies** that the L3 door injects into every query plan
> and the connection layer translates into DBMS transaction modes — instead of an
> application-level library bolted on top (the 1С-БСП shape).

---

## 1. Motivation — why platform, not library

A library (the БСП shape: period-close checks as application subscriptions) can only
**check**. A platform-level declaration can be **exploited**:

- the engine *routes* queries over frozen periods to the totals table / an eternal cache;
- the engine *injects* row-level predicates server-side, so paging / aggregates / COUNT
  stay honest and restricted rows never leave the DBMS;
- the connection layer *opens read-only transactions* for read-only users (on Firebird
  this changes the engine's whole relationship with the session — see §7);
- the AI agent *generates* one policy + one binding instead of wiring library code.

A library can never feed the query planner. That is the whole argument.

Enforcement point: **all reads and writes already pass through the single L3 door**
(`ibDataQueryBuilder` — `Execute` / `Upsert` / `Delete`). A check placed there cannot be
bypassed by application code; below the door there is only physics.

---

## 2. Core model — three entities, no tree

The decisive difference from the 1С shape ("a role is a monolith of checkboxes with RLS
templates baked in"): **the policy is the atom, the role is a label.**

1. **Policy** — a self-contained declaration: *what* (metaobject / scope), *under which
   condition* (a predicate over metadata paths, a period boundary), *effect* (read /
   write / read-only / routing hint). A policy knows nothing about who it applies to.
2. **Binding** — a separate entity attaching a policy to a recipient: a user, a group,
   a role, or **everyone** (global). Period-close freeze = a globally-bound policy;
   per-group boundaries = the same policy bound to groups. No "subfolders".
3. **Role** — a *named set of bindings*: packaging convenience ("accountant" = a bundle
   attached in one gesture), not a mechanism. The door computes; the role does not.

Hierarchies ("roles under a policy" / "policies inside a role") are a trap: access
rights, period close, and future plugin rules are **orthogonal aspects** that intersect
on the same data — a tree forces duplicated branches. The flat model converges with
AWS IAM (policy / attachment / role) and Kubernetes RBAC (Role / RoleBinding) —
convergence with the canonical shape of a mature access system, same as Query/Selection.

Policies are **first-class data**: serialized in the configuration text format, diffed
by Compare/Merge, generated by the agent, validated against the metadata tree before
execution.

### Composition semantics

- **Within one aspect** (e.g. several role-bound visibility policies reaching one user):
  **OR** — permissive model, every role *adds* visibility. The inverse (AND) makes
  adding a role *shrink* rights — counter-intuitive, always ends in pain.
- **Between aspects** (rights AND period-close AND plugin rules): **AND** — different
  concerns must all pass.

---

## 3. Policy SPI — a provider registry

The door does not own the rules; it owns the **invocation point**. Policy *providers*
register in a platform registry; at plan-build time the door consults all of them with
(session, metaobject, operation kind) and composes the answers:

| Provider | Contributes |
|---|---|
| Roles | visibility / write predicates per metaobject |
| Period close | write-deny verdicts, read-only verdicts, routing hints |
| Plugins (future) | anything — territorial access, workflow states, … |

"БСП inverted": the platform owns the socket, subsystems own the rules. The policy SPI
is the same extensibility contract for *rules* that the queryable contract is for
*sources* — and both plug into the same door.

---

## 4. Period close — the boundary ladder

Two operations, one policy, different bindings — and a **critical distinction**:

- **Soft boundary ("close for a group")** — a *ban*: policy table `group → date`.
  Pure write-gate (verdict in the write door). Grants **no immutability** — another
  group still writes — so it enables **no read optimisations**.
- **Hard boundary ("close for everyone") = freeze** — *immutability as a fact*. Nobody
  writes before D, no exceptions. Only the freeze unlocks the read-side machinery.

**Effective boundary for a user** = `max(freeze, most-permissive-of-their-group-bounds)`
— permissive across the user's groups (like role OR), strict against the freeze (nobody
overrides the freeze; that is what makes it a freeze).

"A group's own policy" and "a write check" are **the same thing** in this model: the
group policy *is* the write check, expressed declaratively. There is no separate
checking mechanism.

### What the freeze unlocks (read side)

1. **Routing** — a query whose range lies entirely inside the frozen zone reads ONLY
   the totals table; a range crossing the boundary splits into "totals + live tail".
   The freeze is what makes totals *trustworthy* (final, never re-verified) instead of
   "a cache on good faith".
2. **Eternal cache** — results over frozen ranges are immutable → cacheable without
   invalidation (key: query shape + params + **policy version**). A year-report over a
   closed year computes once.
3. **Physics** — frozen periods = cold partitions (PG); totals splitter rows collapse
   (no hot writes will ever return there).

**Operational UX**: the accountant advances group boundaries while reconciling, then
advances the freeze — and that single gesture triggers totals finalisation, splitter
collapse, and eternal-cache eligibility. The management action and the optimisation
are the same button.

### Totals-table contention (design-in from day one)

Totals create their own hotspot: thousands of users posting against one
counterparty×month row = a row-lock convoy. Two standard remedies, both planned into
the totals schema **from the start** (retrofitting means a schema migration under load):

- **Splitter**: N rows per totals key; writers update a random one, readers SUM over N.
- **Deferred maintenance**: documents write only movements (fast); a daemon job folds
  totals in the background — posting never waits for aggregation.

## 5. RLS — flat predicates through the same lowering

A read policy is a declarative condition over metadata paths
(`Counterparty.Manager = CurrentUser`, `Organisation IN (…)`) lowered by **the same
pipeline as a user WHERE**: `BuildWherePredicate` + `ibRefJoinChain` (dot-walk paths in
the policy become the same LEFT JOINs over `_RRRef`; composite references = the same
branch walk + COALESCE). The policy is just another AND-node in the predicate tree.

Why the L3 door is the uniquely right place — five properties:

1. **One door = zero bypass** — lists, forms, text queries, LINQ, reports, selector
   drill-downs, and every future consumer (L5, BI) inherit enforcement automatically.
2. **The door sees the whole plan** — the predicate is stamped onto **every** source in
   the plan (join targets of dot-walks, composite branches), closing the classic leak
   "restricted data escapes through a dotted attribute of a joined table".
3. **Before aggregation for free** — the door owns the aggregation pipeline, so the
   predicate naturally enters WHERE, not HAVING; SUM/COUNT never reveal foreign rows.
4. **Session context at hand** — the user comes from `ibSession::Current()`; the
   allowed-org list computes once per session and rides as a Param → SQL text stays
   stable → prepared-statement caches live; the DBMS prunes indexes/partitions.
5. **External sources too** — `ComputeRows` receives the door's conditions, so the
   policy reaches computed / external queryables (pushed into the connector or applied
   at materialisation) — one policy for own and foreign data, mandatory for BI.

**Anti-pattern to never repeat** (the 1С РЛС lesson): injecting correlated permission
subqueries per query — legendary performance death. Our injection is a **flat sargable
predicate**; RLS here *shrinks* plans (less data), it does not kill them.

Native PG `CREATE POLICY` remains an optional second echelon (covers direct-to-DB
access bypassing the platform); the primary mechanism is ours at L3 — portable
(Firebird has no native RLS) and plan-controlled.

## 6. Enforcement chain — policy to physics

```
policy verdict (read-only for this user / this data)
  → L3 door (predicates, verdicts, routing)
    → holder checkout with intent (Read / Write)
      → pool opens the transaction in the matching mode (TPB / SET TRANSACTION)
        → (horizon) read-only sessions route to a replica
```

The user-level declaration "read-only" propagates down to a DBMS transaction flag with
a tier-specific win at every step — the door contributes predicates, the pool
contributes routing, the DBMS contributes its GC mode.

**Grain = the transaction, not the DB user.** Per-user GRANTs would break the pool
(one technical DB user, connections flow between threads). A separate read-only DB user
for a dedicated *reporting pool* is an option for hardened installations, not the base.

System writes of a "read-only" user (audit log, settings, lock heartbeat) travel their
own technical paths (the logger already owns a separate SQLite) — unaffected.

---

## 7. Read-only transactions — what the DBMS actually gives

Not a different query *plan* — a different *transaction mode*, and on our DBMSes the
mode is worth a lot:

- **Firebird**: a read-only read-committed transaction is **pre-committed** — it does
  not hold oldest-active, therefore **does not stall garbage collection**. The
  "hour-long year report bloats version chains" problem *vanishes* for declared reads.
  One TPB flag.
- **PostgreSQL**: read-only transactions take no real XID and write no WAL (cheaper at
  hundreds of readers); `SERIALIZABLE READ ONLY DEFERRABLE` runs long reports outside
  serialisation conflicts entirely; and read-only is the *ticket to the replica* — a
  standby physically cannot serve anything else.
- **Defence in depth**: if a bug ever lets a write slip past a policy verdict, the
  read-only transaction rejects it at the DBMS level. Policy duplicated by physics.

## 8. Operational design — borrowed deliberately

From SELinux (explicitly considered as prior art):

- **MAC / DAC split** → freeze (nobody overrides) vs role policies (permissive).
- **Enforcement below the application** → the door + the transaction mode.
- **Permissive mode — in the arc from day one**: a new policy activates as
  "log-but-allow" (through the existing audit-log subsystem); a week of "who would have
  been blocked" observation, then enforcing. Rights rollout with zero broken workplaces.

And the SELinux *failure* to avoid (the `setenforce 0` destiny): policies must read as
sentences ("operators cannot write before Nov 30"), the model stays at exactly three
entities, and the agent explains every denial with a trace (policy → binding →
verdict). A denial without an explanation is the road to "turn your policies off".

Other operational requirements:

- **Policy version in every cache signature** — prepared statements, the eternal cache:
  a rights change must never serve a foreign cached result.
- **Privileged sessions are an explicit flag** — designer, migrations, scheduled daemon
  jobs read without RLS *by declared mode*, not by accident; otherwise one day a
  background job computes totals over half the data.
- **Read-only verdict surfaces in the UI** — a document from a frozen period opens
  read-only (a lock icon up front), instead of failing at save time. The form asks the
  door; the door asks the providers; zero application code.
- **Monitoring**: oldest-active-transaction age as a first-class metric — the early
  signal of a long snapshot (and, post-arc, of a missing read-only declaration).

## 9. Recommended build order

The arc slots in after the current phase-D tail of L4-2, intertwined with the
totals-table arc (they share the freeze):

1. **Policy model + serialization** — the three entities in metadata, text-format
   round-trip, Compare/Merge support. No enforcement yet; the data shape first.
2. **Door verdict seam (policy SPI)** — the registry, the (session, object, op)
   consultation call in `Execute` / `Upsert` / `Delete`, AND/OR composition. With a
   trivial built-in provider for tests.
3. **Period-close provider** — boundary ladder, effective-boundary math, write-gate
   verdicts; permissive mode through the audit log from the first build.
4. **Totals tie-in** — freeze ↔ totals finalisation / splitter collapse / routing
   (this is where the policy arc and the totals arc are one work item).
5. **RLS provider** — flat predicate injection through the lambda/text lowering reuse;
   per-source stamping incl. dot-walk join targets; policy version in cache keys.
6. **Read-only transaction flag** — intent on holder checkout → TPB / SET TRANSACTION;
   FB GC relief measured (before/after on a long report under concurrent writes).
7. **(Horizon)** replica routing for declared-read sessions; native PG policies as the
   second echelon for hardened installs.

Steps 1–3 are independent of the totals arc and deliverable on the current tree;
step 4 is the natural junction point; steps 5–6 are independently shippable increments.
